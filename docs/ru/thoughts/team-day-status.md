У каждого сотрудника свой агент hermes, а у каждого агента свой trip2g. Утром агент спрашивает своего человека, что тот планирует, вечером — как прошёл день. Ответ он сохраняет заметкой. Агент руководителя забирает эти заметки у всех сотрудников в свою базу и собирает одну страницу дня команды.

Ни созвона-летучки, ни формы. Никто никому не шлёт отчёт.

![[team-day-dashboard.png|Страница руководителя: по строке на сотрудника, собрана из заметок их агентов]]

## Два вопроса в день

Вопросы ничего не стоят. Cron-задача hermes с `no_agent` запускает скрипт, который печатает готовый текст, и задача отправляет его человеку в Telegram. Модель не запускается, токены не тратятся:

```
09:00  daily-morning  → «Что сегодня в планах?»
18:00  daily-evening  → «Как прошёл день? Что сделано, где нужна помощь?»
```

Важен один флаг: `attach_to_session`. Без него вопрос живёт только в сессии самой cron-задачи, и ответ человека приходит агенту без вопроса перед ним. С ним вопрос лежит в истории чата, и ответ понимается как ответ.

## Заметка дня

Агент пересказывает каждый ответ несколькими короткими строками. Саму переписку он не хранит:

```markdown
# 2026-10-18 — Маша

## План
- Дописать коммерческое предложение для «Альфа-Логистик».
- В 15:00 провести созвон с «Альфа-Логистик».

## Итог
- Коммерческое предложение отправлено.
- Созвон проведён; клиент запросил скидку 10%.

## Нужна помощь
- Требуется согласование руководителя на скидку 10%.
```

Утро заполняет «План», вечер — «Итог» и «Нужна помощь». Один файл на день: `daily-sync/YYYY-MM-DD.md`.

## Открыто руководителю, и только это

Frontmatter-патч кладёт папку в отдельный подграф:

```jsonnet
{ subgraph: "daily_sync" }
```

Агент сотрудника выпускает ключ федерации через `federation_share` только на `daily_sync` и передаёт его агенту руководителя, тот подключает ключ один раз. Руководитель видит дни, и больше ничего из базы сотрудника: ни заметок, ни памяти, ни других подграфов. Отзыв одного ключа всё закрывает.

## Веер, потом копия

`federated_note_html` читает одну заметку из одной базы, так что тридцать сотрудников — это тридцать вызовов. Путь задан соглашением, и ничего не нужно искать:

```
для каждой подключённой базы:
    federated_note_html(kb_id, "daily-sync/<сегодня>.md")
    → записать team/<человек>/<сегодня>.md, если изменилось
```

Это раз в час делает скрипт, из ещё одной cron-задачи с `no_agent`. Поиск здесь не годится: `federated_search` без явного списка `kb_ids` опрашивает не больше семи баз (`--federated-fanout-limit`), по пять одновременно, по пять секунд на каждую, а остальные пропускает.

Руководитель держит копию, а не читает вживую. Это намеренно. Статус дня — факт с датой, его потом никто не правит, поэтому копия не устаревает. Если вечером база сотрудника недоступна, на странице остаётся его день из последней копии. А модель руководителя читает локальные заметки, а не тридцать пиров.

## Страница

Ещё одна cron-задача, уже с моделью, читает сегодняшние копии и пишет `dashboards/team-today.md`: по строке на сотрудника, список тех, кому нужна помощь, и тех, у кого сегодня нет статуса. Пустой день — тоже сведения, поэтому агент никого не дёргает.

## Чему научил первый прогон

- **Вопрос должен быть в истории.** Без `attach_to_session` ответ «дописываю КП» приходит агенту как сообщение из ниоткуда.
- **Скажите, какой скил берёт ключ.** Сообщение с блоком подключения сначала ловит общий скил «подключить базу знаний». Агенту руководителя нужна постоянная инструкция: такие сообщения — про статус команды.
- **Имя — от человека.** Пока человек не поправит, агент берёт имя из профиля Telegram.
- **Приватность — часть устройства.** Человек знает, что руководитель читает его день, а в заметке пересказ, никогда не переписка.
